# /forge — спецификация движения (motion spec)

Статус: спецификация для утверждения. Ни один файл кода не изменён — это описание поведения, на которое будет опираться реализация после согласования `design-system.md`.

Контекст прочитан: текущий паттерн движения на сайте — `components/motion/FadeIn.tsx` (opacity+y+scale через Framer Motion, `whileInView`, только transform/opacity), `components/forge/ForgeIntro.tsx` (процедурная canvas-анимация ~3.4s поверх уже отрендеренного Hero, `prefers-reduced-motion` — полный пропуск), `components/motion/ScrollProgress.tsx` (`useScroll`+`useSpring`, motion value вне React state). Эта база технически годная — новая система движения для партии в шахматы наследует те же принципы (compositor-only свойства, contentful-first, reduced-motion=выключить сложное), но добавляет камеру и «доску» как сквозной элемент.

## 1. Длительности — три яруса

| Ярус | Диапазон | Примеры на /forge | easing |
|---|---|---|---|
| Интерфейсные микро-реакции | 180–300ms | hover кнопки, focus-ring, нажатие, подсветка активной клетки | `ease-out` (`cubic-bezier(0.16,1,0.3,1)` — уже используется в `FadeIn`/`StickyForgeCTA`, оставляем как стандарт) |
| Смысловые переходы | 500–900ms | ход пешки на новую клетку, появление золотой траектории, "трещина" на фигуре, смена секции текста | `cubic-bezier(0.16,1,0.3,1)` (тот же — сайт уже унифицирован на нём) |
| Кинематографические сцены | 2–4s | вступление (аналог текущего `ForgeIntro`, ~3.4s), подъём камеры к финалу, выход короля за границу доски в самом конце | составные — несколько тактов внутри одной сцены, каждый такт всё равно строится из 500–900ms шагов, а не одной длинной кривой (легче собрать, легче укоротить под reduced-motion) |

Никаких длительностей вне этих трёх диапазонов не вводим — если анимация "не укладывается", это сигнал разбить её на шаги, а не растянуть цифру.

## 2. `prefers-reduced-motion` — обязательное поведение

Правило: `reduce` отключает **сложное** движение, а не всё вообще — по факту это означает три уровня деградации, не бинарный переключатель:

1. **Кинематографические сцены (2–4s) — полностью выключены.** Ровно как сейчас `ForgeIntro`: `if (reduce) { setPhase("skipped"); return; }` — контент виден с первого кадра, ноль анимации. Тот же паттерн для сцены подъёма камеры и финального выхода короля: при reduce они не проигрываются, конечное состояние (камера сверху, король за рамкой доски) рендерится статично.
2. **Смысловые переходы (ход фигуры, трещины, смена цвета металла) — заменяются мгновенным or кросс-фейдом ≤150ms.** Пешка на новой клетке появляется сразу, без анимации перемещения; подсветка активной клетки — просто мгновенно активный `background-color`, без transition. Это не "убрать анимацию совсем", а свести её к простому fade, который уже разрешён глобальным CSS-правилом сайта.
3. **Интерфейсные микро-реакции — можно оставить**, но урезанные: hover/focus остаются (это не "движение" в смысле укачивания, а функциональная обратная связь), но `translateY` на hover кнопки убирается (уже это делает текущий класс `motion-reduce:transform-none` на `Button.tsx`, паттерн просто переносится в новые компоненты).

Технически: сайт уже задаёт глобальный fallback в `app/globals.css`:

```css
@media (prefers-reduced-motion: reduce) {
  html { scroll-behavior: auto; }
  *, *::before, *::after {
    animation-duration: 0.001ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.001ms !important;
    scroll-behavior: auto !important;
  }
}
```

Этого достаточно для CSS-анимаций/transition, но **недостаточно для JS-driven сцен** (Canvas, Framer Motion `animate`/scroll-linked, любой rAF-цикл) — те не подчиняются CSS `!important`. Каждый JS-анимационный компонент обязан сам проверять `window.matchMedia("(prefers-reduced-motion: reduce)").matches` при монтировании (как уже делает `ForgeIntro`) и либо не запускать цикл вовсе, либо рендерить статичный конечный кадр. Это правило, не опция — каждый новый motion-компонент на /forge (шахматная сцена, камера, траектория) обязан пройти этот чек перед тем как получить rAF/scroll listener.

## 3. Разрешённое движение (белый список)

Только это — без импровизаций поверх списка:

1. **Пешка делает один ход при переходе к разделу.** Не непрерывное скольжение по всей длине скролла — дискретный шаг между определёнными позициями на доске, привязанный к смене секции (Intersection Observer / scroll-snap на секцию, не к каждому пикселю скролла).
2. **Активная клетка подсвечивается.** Смена `background-color`/`box-shadow` клетки, куда встала фигура — 500–900ms переход, не мигание.
3. **Старые линии движения исчезают.** След предыдущего хода (тонкая золотая линия) fade-out 500–900ms при появлении нового хода — не накопление бесконечных линий на доске.
4. **Фигура получает трещины.** Статичная текстура/SVG-паттерн трещин, который проявляется (opacity 0→1, 500–900ms) на переходе между стадиями сюжета — не процедурная генерация трещин в реальном времени.
5. **Металл меняет цвет.** Заливка/оттенок фигуры сдвигается по палитре (напр. `graphite` → `metal-gold` к финалу) через `transition: filter/color` или кроссфейд двух SVG-слоёв — 500–900ms на шаг.
6. **Камера поднимается над доской.** См. раздел 5 — реализуется как CSS `perspective`+`transform`, привязанная к scroll-прогрессу секции, не свободная 3D-навигация.
7. **Золотая траектория показывает план.** SVG `path` с `stroke-dasharray`/`stroke-dashoffset`, "рисуется" за 500–900ms при входе секции в вьюпорт — уже есть похожий по духу приём в текущем сайте (`ChessPiece` как `currentColor` SVG), просто добавляется анимация обводки.
8. **В финале Король выходит за границу.** Однократная кинематографическая сцена (2–4s) в самом последнем экране — фигура смещается за пределы визуального контура доски, доска может слегка уменьшиться/уйти на задний план. Проигрывается один раз, не зациклена.

## 4. Запрещённое движение (чёрный список)

1. Бесконечное вращение фигур (или чего угодно) — никаких `infinite` keyframes на смысловых элементах.
2. Прыгающие/пружинящие элементы без функциональной причины (никаких decorative bounce).
3. Параллакс на каждом объекте — максимум один слой параллакса на сцену (фон доски отдельно от переднего плана), не параллакс-суп из пяти слоёв.
4. Резкие приближения (hard cut zoom) — любое изменение масштаба идёт по одной из трёх длительностей выше, никогда не мгновенно (кроме reduced-motion деградации, где это осознанный компромисс, не эстетика).
5. Сложные переходы, мешающие чтению — если анимация идёт одновременно с тем, что пользователь должен прочитать текст, анимация обязана быть периферийной (фон/фигура), не на самом тексте.
6. Постоянное движение фона — никакого зацикленного shimmer/gradient-shift на фоне секций, где есть текст для чтения. (Существующий `.grain-overlay`/`animate-grain` — статичный зашумлённый паттерн, не яркое движение; такого рода тонкая текстура допустима, "постоянное движение" здесь про заметное, отвлекающее движение, не про grain.)
7. Звук без явного согласия пользователя (никакого autoplay-звука вообще; если когда-либо будет звук — только по явному тычку в контрол "включить звук").
8. Обязательная анимация для понимания смысла — любая информация, которую несёт анимация (ход фигуры, траектория, число), обязана быть считываемой и без неё (статичный текст/подпись/финальное состояние). Это прямое следствие правила "текст и кнопки работают независимо от 3D" в разделе 6.

## 5. Камера — без тяжёлого 3D

Задача: в начале страницы взгляд «почти с уровня пешки» (низкий, интимный, вплотную к доске), к середине — постепенный подъём, в финале — вид сверху, с выходом короля за границы доски.

Это не требует WebGL/Three.js как обязательного условия — достаточно связки `perspective` + `transform` на CSS, управляемой scroll-прогрессом секции (через тот же механизм, что уже использует `ScrollProgress.tsx` — `useScroll`/`useSpring`, motion value вне React state, ноль лишних ре-рендеров):

```css
.forge-camera-scene {
  perspective: 1400px;
  perspective-origin: 50% 85%; /* низкая точка схода в начале — "с уровня пешки" */
}
.forge-board {
  transform-style: preserve-3d;
  transform: rotateX(var(--camera-tilt, 62deg)) translateY(var(--camera-lift, 0px)) scale(var(--camera-scale, 1));
  transition: transform 700ms cubic-bezier(0.16,1,0.3,1);
}
```

Логика по ходу страницы (значения — стартовая точка для тюнинга, не финал):

| Стадия | `--camera-tilt` | `--camera-lift` | `--camera-scale` | Ощущение |
|---|---|---|---|---|
| Пешка (начало) | 68–72deg (доска почти "на ребро", видно немного) | 0 | 1.05 (чуть крупнее — близко) | взгляд почти с уровня фигуры |
| Осознание / план | 55–60deg | небольшой + | 1.0 | доска начинает раскрываться |
| Кузня / стратегия | 35–42deg | средний + | 0.92 | камера явно приподнялась, видно структуру доски |
| Король (финал) | 8–15deg (почти план сверху) | максимальный + | 0.85, затем фигура короля сама выходит за `overflow` контейнера доски | вид сверху, король буквально покидает кадр доски |

Технически: `--camera-tilt`/`--camera-lift`/`--camera-scale` — CSS custom properties на обёртке сцены, обновляются через `useScroll({ target, offset })` + `useTransform` (Framer Motion) при пересечении секций, не на каждый пиксель скролла всей страницы — три-четыре стадии, не непрерывная функция от 0 до 100% скролла всего документа. Это держит пересчёт дешёвым (несколько дискретных `useTransform` шагов, не постоянный rAF-луп) и не создаёт укачивания.

Правило слоёв: доска (`.forge-board`) — один 3D-контекст (`transform-style: preserve-3d`), фигуры внутри неё — плоские SVG/PNG на `translateZ`, не отдельные 3D-меши. Это и есть согласованный технический потолок — CSS 3D-transform в духе `BookMockup3D.tsx`, не полноценная 3D-сцена. Финальный "выход короля за границу доски" — фигура получает `translateZ`/`translateY` за пределы `.forge-board`, родительский контейнер должен **не** обрезать (`overflow: visible`) в этой конкретной сцене (осознанное, единственное место на странице, где мы это разрешаем).

Для мощных устройств (см. раздел 6) допустима замена этой CSS-сцены на настоящий WebGL/Three.js рендер той же доски — но это отдельная реализация, не обязательное требование; CSS-версия обязана работать сама по себе как полноценный, не "урезанный", опыт.

## 6. Деградация по мощности устройства — конкретные признаки, не гадание

Стратегия: определить "профиль" устройства один раз при монтировании страницы (не на каждый кадр), выставить `data-motion-tier="full" | "reduced" | "static"` на корневой обёртке /forge, и дальше все motion-компоненты читают этот атрибут вместо того, чтобы каждый сам гадал.

### 6.1 Признаки, по порядку приоритета (первый сработавший — решает)

1. **`prefers-reduced-motion: reduce`** → всегда `static`, независимо от мощности устройства. Это явно выраженное пользователем предпочтение, оно перекрывает все остальные эвристики.
2. **`navigator.connection?.saveData === true`** (Data Saver включён) → `static`. Пользователь явно просит экономить трафик — тяжёлые сцены/видео не грузим.
3. **`navigator.deviceMemory` (если доступен, Chrome/Android; в Safari/iOS не определён — тогда пропускаем этот пункт и идём дальше по списку, не считаем отсутствие признаком слабости)**:
   - `< 4` (ГБ) → `reduced`.
   - `>= 4` → не блокирует `full`, но сумма с п.4 решает.
4. **`navigator.hardwareConcurrency` (число логических ядер)**:
   - `<= 4` → `reduced`.
   - `> 4` → допускает `full`.
5. **`matchMedia("(pointer: coarse)").matches` И `matchMedia("(hover: none)").matches`** (типичный touch-без-hover профиль — большинство телефонов) → по умолчанию `reduced`, не `static` (это не про мощность, а про форм-фактор: сложная 3D-сцена на телефоне и физически не нужна — user всё равно не наводит курсор, драматургию несёт скролл, не hover). Планшеты/десктопы с hover остаются кандидатами на `full`.
6. Если ни один из явных "слабых" признаков не сработал (deviceMemory ≥4 или недоступен, hardwareConcurrency >4, есть hover, не saveData, не reduced-motion) → `full`.

Итого дерево: `reduced-motion` → `static`; `saveData` → `static`; иначе (`deviceMemory<4` ИЛИ `hardwareConcurrency<=4` ИЛИ (`coarse pointer` И `no hover`)) → `reduced`; иначе → `full`.

Такая логика собирается один раз в клиентском хуке (например `useMotionTier()`), никаких предположений по User-Agent / "это айфон, значит слабый" — только измеримые API. Все проверки — со страховкой на `typeof window === "undefined"` (SSR) и на отсутствие API (Safari не отдаёт `deviceMemory`) — отсутствие API не равно "слабое устройство", это явно прописано в п.3.

### 6.2 Что рендерится на каждом уровне

| Уровень | Кинематографические сцены (Intro, финал) | Камера | Ход фигуры/трещины/траектория | Технология доски |
|---|---|---|---|---|
| `full` | canvas/WebGL-версия допустима (не обязательна) | scroll-driven CSS 3D-camera (раздел 5), полный диапазон | все переходы 500–900ms анимированы | опционально Three.js-рендер, иначе CSS 3D |
| `reduced` | статичный ключевой кадр (последнее состояние сцены) вместо проигрывания, либо укороченная CSS-версия ≤1.5s | camera work урезан до 2 стадий (начало/конец), без промежуточных | переходы остаются, но короче (≤400ms) и без 3D-трансформаций фигур (только opacity/color) | CSS 3D исключительно (никакого Three.js) — либо статичное 2D-изображение доски со сменой активной клетки |
| `static` | не рендерятся — статичная картинка/финальный кадр сразу | камера не меняется — один фиксированный "средний" ракурс на всю страницу | без анимации, мгновенная смена состояния | 2D SVG/изображение доски, ноль transform в 3D |

### 6.3 Ассеты

- `full`/`reduced`: SVG для доски и фигур (уже используемый на сайте паттерн — `PIECE_PATHS` в `app/forge/page.tsx`, currentColor fill) — векторное, лёгкое, не требует отдельных изображений на плотность экрана.
- Если для кинематографических сцен (Intro/финал) понадобится видео-фрагмент вместо canvas/WebGL — только на `full`, формат AV1/H.265 с WebM/MP4 fallback, `preload="none"`, запускается по `IntersectionObserver`, не автоматически на загрузке страницы. На `reduced`/`static` видео не грузится вообще (даже poster-кадр — обычным `<img>`, не через `<video>` тег, чтобы не тянуть видео-декодер).

## 7. Независимость текста и кнопок от 3D

Обязательное требование дословно: контент обязан загружаться и работать, даже если motion-слой не загрузился/упал/отключён.

Практические следствия для реализации (фиксирую как чек-лист для будущего PR, не для этого документа):

1. Текст, заголовки, CTA-кнопки — обычный DOM (HTML/CSS), не элементы внутри Canvas/WebGL-сцены. 3D/canvas-слой — всегда декоративный, `aria-hidden="true"`, `pointer-events: none`, абсолютно спозиционирован **над или под** контентом, никогда не единственный носитель текста (ровно как уже сделано в `ForgeIntro` — накладка над уже отрендеренным Hero, не замена его).
2. Порядок загрузки: сначала весь текстовый/интерактивный контент (SSR/Server Component, как остальной сайт на Next.js), motion-компоненты — `"use client"`, гидратируются позже, без блокировки первой отрисовки. Это уже архитектурный паттерн сайта (`FadeIn`, `ForgeIntro`, `ScrollProgress` — все `"use client"`, оборачивают уже существующий серверный контент).
3. Любая ошибка в motion-коде (canvas контекст недоступен, WebGL не поддерживается) — try/catch с graceful fallback на `static`-состояние, не белый экран/краш всей страницы (та же логика, что уже есть в `ForgeIntro`: `if (!ctx) { setPhase("skipped"); return; }`).
4. Кнопки (CTA) никогда не зависят от motion-цикла для клика — `href`/`onClick` работают с первого кадра гидратации, независимо от того, доиграла ли кинематографическая сцена. Это уже так на сайте (`StickyForgeCTA`, `PrimaryCta`) — сохранить этот принцип.

## 8. Бюджет производительности (LCP/INP/CLS)

| Метрика | Цель | Как обеспечиваем |
|---|---|---|
| **LCP** (Largest Contentful Paint) | ≤2.5s на 4G/mid-tier телефоне | Hero-текст/заголовок — не изображение и не внутри canvas (LCP-кандидат должен быть обычным DOM-текстом или `<Image priority>`, как уже сделано в текущем hero `app/forge/page.tsx` через `next/image` с `priority`). Кинематографическая интро-сцена рендерится **поверх** уже видимого Hero (тот же паттерн, что `ForgeIntro` сейчас) — она не блокирует и не задерживает LCP-элемент. Никакого `display: none → block` motion-контента, который перекрывал бы реальный LCP-кандидат до его отрисовки. |
| **INP** (Interaction to Next Paint) | ≤200ms | Все scroll-driven анимации — на motion values вне React state (`useScroll`/`useSpring`/`useTransform`, тот же подход, что уже в `ScrollProgress.tsx`), не через `setState` в scroll-хендлере (кроме уже существующего осознанного случая в `StickyForgeCTA`, где `setState` дискретный, не на каждый пиксель). Никаких тяжёлых синхронных вычислений (генерация трещин, физика частиц) в обработчике клика/скролла — только предвычисленные/анимируемые CSS custom properties. Canvas-сцены — капped частиц (как сейчас `SPARK_COUNT = 26` в `ForgeIntro`), не десятки тысяч. |
| **CLS** (Cumulative Layout Shift) | ≤0.1, по факту стремимся к 0 | Motion-слои (canvas/3D-камера) — всегда `position: absolute`/`fixed` поверх уже занимающего место контента, никогда не влияют на высоту документа при появлении/исчезновении (тот же паттерн, что уже описан в комментарии `ForgeIntro`: "Sits absolutely positioned over the Hero section... so it can never cause layout shift"). Все изображения — с заданными `width`/`height` или `fill` в контролируемом по размеру родителе (как уже везде на сайте через `next/image`). Веб-шрифты — уже загружены через `next/font` (значит `font-display` управляется фреймворком, минимальный CLS от шрифтов) — сохранить этот подход, не добавлять сторонние `<link>` на Google Fonts CDN. |
| **JS-бюджет motion-слоя** | Доп. вес от новой 3D/canvas системы ≤35KB gzip сверх уже используемого Framer Motion (который на сайте уже есть — не считаем повторно) | Никакого Three.js в бандле по умолчанию — только динамический `import()` внутри ветки `full`-tier (раздел 6), с `next/dynamic({ ssr: false })`, чтобы `reduced`/`static`-пользователи и боты/SSR вообще не тянули эту зависимость. |
| **Изображения/видео сцен** | LCP-путь не должен включать видео | Постер-кадр интро/финальной сцены — статичный AVIF/WebP, видео (если будет) — грузится только после того, как секция попала в вьюпорт и tier === "full". |
| **Общий принцип** | «Дорогая» сцена — привилегия, не право по умолчанию | Каждая кинематографическая сцена (2–4s) обязана иметь тестируемый бюджет: до включения в PR — реальный замер Lighthouse/PageSpeed на мобильном профиле (Moto G4 throttling, 4G) на реальной сборке этой секции, не догадка. Если сцена проседает LCP/INP на этом профиле — она уходит в `reduced`-tier по умолчанию для всех, а не только для формально "слабых" устройств. |

## 9. Открытые вопросы к владельцу

1. Раздел 5 (камера): предложенные диапазоны `--camera-tilt`/`--camera-lift` — стартовая гипотеза для тюнинга на реальной доске/фигурах, не финальные числа — нужен визуальный проход в браузере после того, как появится хотя бы одна собранная сцена, чтобы подтвердить ощущение "почти с уровня пешки" → "сверху".
2. Раздел 6: используем ли вообще WebGL/Three.js как опциональный `full`-путь, или сразу фиксируем чистый CSS 3D-потолок для всех устройств (проще, меньше поверхности для багов, но менее эффектно на мощных десктопах)? Технический потолок по вашему прошлому решению — CSS 3D по умолчанию; WebGL — только если вы явно его запросите. Держу это как явную опцию в разделе 6, но по умолчанию буду реализовывать без Three.js, пока не будет прямого запроса.
3. Раздел 3, пункт 4 ("фигура получает трещины") — нужен референс, как именно должны выглядеть трещины (тонкие волосяные линии по металлу vs явные сколы) — это визуальный вопрос, не только про движение, относится скорее к `design-system.md`/референсу, но фиксирую здесь, т.к. без референса анимацию появления трещин не собрать.
